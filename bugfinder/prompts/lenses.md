# Lenses (core catalog — domain-neutral)

Failure-mode classes for hypothesis agents. Each round, the orchestrator
instantiates `03-hypothesis` with one lens × one seed.

The material a hypothesis agent receives for its lens is assembled from
three layers:

1. **Core lens** (this file) — the failure mode itself, defined
   domain-neutrally. These are universal: every codebase can compute a
   wrong number, serve stale state, or swallow an error.
2. **Pack extensions** (`packs/*.md`) — per-lens signature lists for a
   domain (ML/research, engineering tooling/services, …). The usage
   model's *domain profile* section declares which packs apply — possibly
   per-module, since real codebases mix domains (a research core with
   engineering glue around it).
3. **Codebase-specific signatures** — generated by the usage-model phase
   from this repo's actual invariants and reviewed by `02`. The sharpest
   layer, because it is derived from the code rather than hardcoded.

Signatures at every layer are *priming cues, not a checklist*: they tell
the agent what this failure mode tends to look like, but the lens
definition governs. Absence of a listed signature is not clearance, and a
match on a signature is not yet a finding.

Per-lens budgets should adapt over time: the orchestrator tracks each
lens's confirmed-vs-refuted ratio on this codebase and shifts fanout
toward lenses that pay.

---

## wrong-math — Calculation & aggregation correctness

Code that runs and returns a number — the wrong number. The flagship lens
for silent wrongness.

Signatures:
- Off-by-one in ranges, windows, slices, and boundary arithmetic;
  inclusive vs exclusive conventions mixed across a call boundary;
  fencepost errors when converting between representations (indices ↔
  offsets ↔ spans).
- Unit and scale mismatches: seconds vs milliseconds, bytes vs KB,
  fraction vs percent, degrees vs radians — anywhere two conventions meet.
- Integer division/truncation, rounding direction, accumulating in a
  precision narrower than the result deserves.
- Aggregation weighting: mean-of-means vs pooled mean over unevenly-sized
  groups; denominators that include entries the numerator excluded.
- Comparisons against a value that can legitimately be zero/negative when
  the code assumes it can't.

Where it hides: aggregation/summary utilities, metric or accounting code,
conversions between formats or coordinate systems.

## data-alignment — Parallel structures & selection integrity

Operations that must keep two or more structures in lockstep, and
selections that must be consistent.

Signatures:
- Filter, sort, dedup, or truncation applied to one of two parallel
  structures (items and their labels/metadata/ids) after the pairing was
  established.
- Joins/merges on a wrong, non-unique, or un-normalized key (case,
  whitespace, unicode); index-based association that doesn't survive a
  reorder.
- Chunking/pagination dropping or duplicating boundary items; resumption
  logic re-processing or skipping.
- The same subset selected twice by code that assumes the selections are
  independent (or vice versa).

## state-staleness — Caching, mutation, staleness

Signatures:
- Cache/memo keys missing an input that affects the result — first call
  wins forever.
- Mutable default arguments; functions mutating caller-owned
  structures in place while appearing pure.
- Module/global state carrying across calls, requests, or runs
  (registries, `functools.cache` on methods, class attributes as scratch).
- Derived artifacts (files, indexes, compiled outputs) re-read without
  invalidation when their sources change; partial writes on interrupt
  read back as complete.

## api-contract — Docs/contract drift

Signatures:
- Docstring, README, help text, or type hints say X; code does Y
  (defaults, units, return types, error behavior).
- Renamed/reordered parameters where old call sites, docs, or configs
  survive; permissive kwargs/options swallowing typos of real names.
- Copy-paste drift between sibling implementations that promise the same
  interface (two backends, two subclasses, two commands) but diverge.

Note: the *fix* may be to the doc rather than the code — still a finding,
but say so in `consequence`.

## boundary-degenerate — Edges users actually hit

Signatures: empty collection/file/result-set, exactly one element, zero
length after filtering, missing-but-optional inputs, a batch/page smaller
than the requested size, the last partial chunk. Constrained by the usage
model: only report edges a real workflow reaches — not adversarial
pathologies.

## config-plumbing — Parameters that don't arrive

Signatures:
- An option accepted, stored, and never read; a setting read but not
  applied on some code path; plumbing lost at a call boundary (accepted a
  list, used only the first element).
- Silent fallback to defaults on lookup failure (a typo'd key returning
  the default instead of erroring); precedence bugs between config
  sources (flag vs env var vs file).
- An option honored in one backend/branch/mode but not its sibling.

Cheap mechanical assist: for a public function's parameters, trace each
one to a use; a parameter with no reachable use is a strong candidate.

## persistence-roundtrip — Save/load & format asymmetry

Signatures: fields dropped or re-defaulted on load; version/format skew
read without error; encoding and newline handling; path assumptions that
break off the author's machine; save-then-load producing an object whose
*behavior* (not just repr) differs from the original.

## resource-environment — The world outside the process

Signatures: leaks (handles, temp files, connections) in long-running use;
unbounded growth that fails at realistic scale (the perf-exception:
report when realistic scale *fails*, not when it is merely slow);
assumptions about the environment — installed tools, network, locale,
timezone, filesystem case-sensitivity, working directory — that turn into
cryptic failures on machines the usage model says this runs on.

## ordering-nondeterminism — Order, time, and concurrency

Signatures: results depending on unordered iteration (set/dict) where
stability is implied; time-dependent behavior (clock reads mid-operation,
DST boundaries); parallel work racing on shared files or state; retries
of non-idempotent operations causing duplicate effects; determinism or
reproducibility promised by the docs/usage model but not delivered.

## silent-failure — Error handling that lies

Signatures: broad `except`/error-swallowing returning a plausible default
(empty list, 0, None) consumed downstream; failures logged at a level
nobody reads while execution continues on partial data; subprocess or
HTTP status codes unchecked; partial success reported as success (3 of 5
inputs processed, no indication); a warning where the usage model implies
users need a hard error.
